# omc-doctor guide

The details that `skills/omc-doctor/SKILL.md` leaves out, one section per `## name` heading. The command `node omc-doctor.mjs guide <name>` prints one section; the skill names the section a rule needs. The text is the one the skill used to carry in its own body.

## channel-unknown

What makes `Channel: unknown` (the rule of Step 1 that says the channel cannot be established):

Step 1 reads `installed_plugins.json` by the rules of the cache commands (section `cache-guard`): it must be a regular file (a FIFO is never opened, and a link to nothing is a file that cannot be read, not an absent one) holding valid JSON, and every entry list under a supported plugin ID must be a non-empty array of entries that each have a non-blank string `version` or `installPath`, and a `version` there must be a semantic version of the grammar of the `Latest:` line (section `latest-grammar`) (`999x.0.0`, `1.2` and `1.2.3.4` are not), as must be the version an entry that has only an `installPath` gets from it when that path names one (the version `package.json` or `.claude-plugin/plugin.json` holds there); a `version` of an entry under another plugin's key is not an OMC version and has to be a non-blank string only; otherwise the channel is unknown (an existing `OMC_PLUGIN_ROOT` that is not a registry install answers first, see section `channel-plugin-dir`). It is unknown too when the registry has no supported plugin ID but holds an empty or non-array entry list under some key, a malformed entry in a list under some other key (the rule of the cache commands, stricter than the installer's resolver, which skips the entries of other plugins: `null`, not an object, a nested array, neither field, or a blank or non-string one; a `null` field counts as missing), or a look-alike key such as `oh-my-claudecode-fork` (the installer's resolver calls that ambiguous, so npm is not assumed from it), unless `OMC_PLUGIN_ROOT` or `CLAUDE_PLUGIN_ROOT` names the active checkout (section `channel-plugin-dir`); and when the two variables name different existing directories (two spellings of one directory are one directory, compared by filesystem identity, and two directories whose names differ only in letter case are two directories on a volume that tells letter case apart, and where the file system gives no inode two spellings that differ only in letter case or Unicode form cannot be told from two directories, so the channel is unknown there too (every path comparison of Step 1); a variable that names no existing directory is ignored, see section `channel-plugin-dir`), whatever the registry holds.

## channel-plugin-dir

How a checkout becomes the install, and which roots Step 1 ignores (the rule of Step 1 for `Channel: plugin-dir`):

A variable whose path is not an existing directory names no checkout (the runtime wrapper skips it and falls through to the managed cache; it skips an existing root without a built HUD too, which Step 1 does not test), so Step 1 ignores it everywhere: it makes no plugin-dir install, no conflict and no channel, and an npm or marketplace install is diagnosed as if the variable were unset. `OMC_PLUGIN_ROOT` is the explicit override, the highest-priority root of the runtime resolution (`omc --plugin-dir` sets it; the runtime skips a root that does not exist), so Step 1 takes an existing one before the registry's channel, whatever the registry holds (a stale supported entry or a registry that cannot be read included), unless it names the install a supported entry pins: its `installPath`, or the cache directory `plugins/cache/<marketplace>/oh-my-claudecode/<version>` that its `version` names, compared by filesystem identity (by exact text where the file system reports inode 0, and unknown where the two spellings then differ only in letter case or Unicode form) so that a link counts, and a letter-case alias counts where the volume ignores letter case. Every path Step 1 compares or reads (the variables, an `installPath`, a pinned version's directory) is resolved in the order the file system reads its components, so `<dir>/shortcut/..` with `shortcut` pointing to `5.9.0/nested` names `5.9.0`, the parent of the link's target, and not `<dir>`, the folder that holds the link (on win32 `..` is folded as text first, as Windows does). That is the registry's own install and the registry decides its channel. Where a directory lies excuses nothing else: another cache version than the pinned one (cache `5.7.0` while the registry pins `5.8.0`), a directory in the cache of another plugin and a path below a version are explicit roots like any other, so Step 1 reports `Channel: plugin-dir` for them, and the cache commands still keep that directory protected. Only when the registry cannot be read completely, a root inside `plugins/cache/` cannot be told from the pinned install, and Step 1 then says `Channel: unknown`. `CLAUDE_PLUGIN_ROOT` is only a locator (Claude Code sets it for marketplace installs too), so it names the checkout only when the registry parses and holds no supported plugin ID (a malformed entry under another key does not make it unreadable here).

## latest-grammar

The grammar of the versions Step 1 reads, and which of them may be a target of an update (the `LATEST` rule of Step 1):

Only a latest version is a target an update is recommended to, so only a latest version must be a semantic version of that grammar: an `npm latest:` value that is not one is a damaged answer and counts as `(unavailable)`: the command itself prints `(unavailable)` for an error, a timeout or a value that is not one, so the line is never a bare string. The versions that report what is installed (a registry `version`, a cache directory name, the `version` of a checkout's `package.json` or `.claude-plugin/plugin.json`) are shown as recorded and ordered by the rule of section `versions-order`, and are never a target. A version a user's data claims, a registry `version` under a supported plugin ID or the `version` of a `package.json` or `plugin.json`, must be a semantic version of that same grammar (one definition, `semver`, in `scripts/omc-doctor.mjs`, used by every command) before it is ordered, because the order ranks a core that is not numeric above the numeric ones: an entry whose `version` is not one is a damaged registry (`Channel: unknown`, no update recommended, nothing moved by the cache commands), and a checkout whose `version` is not one has none (`Installed: (none)`). A cache directory is a version directory only when its name is exactly a semantic version of that grammar (without a `v` and without spaces): Step 1, Step 4, Step 6 and the cache commands take no other name for a version, so `1e3`, `4.15.7L` or `v5.7.0` takes no part in the order, is not counted and is never moved (the runtime reads such a name as 0 or below, never as the newest), and for an entry that has only an `installPath` the last component of the path names the version only when it is one of that grammar (otherwise its `package.json` is read).

## versions-order

Where the versions of Steps 1, 4 and 6 come from, and how scopes, ties and a leading `v` are handled (the ordering rule of Step 1):

Steps 4 and 6 read the cache of the marketplace Step 1 names (`plugins/cache/<marketplace>/oh-my-claudecode`, where `<marketplace>` is the part after the `@` of each supported plugin ID the registry holds: `omc` for the bare `oh-my-claudecode`, and when the registry holds none or cannot be read); with several IDs Step 4 reads the cache of the marketplace whose entry holds the plugin root the session runs (Step 1's match: the highest of them for roots in two marketplaces, `(unknown)` and the check skipped where the match is unknown for any ID, as in Step 1), and only where no entry holds a root (none set, a checkout outside the registry) the last ID of the registry whose cache holds a version; Step 6 prints one line per marketplace, led by its name, and the cache commands take the marketplaces by name. A directory named `<version>.omc-stale-<pid>` (what an interrupted cache relink leaves) is no version in Step 1, Step 4, Step 6 or the cache commands: none of them lists, counts, names it as the newest, dates or moves it. When a plugin ID has entries for several scopes and `OMC_PLUGIN_ROOT` or `CLAUDE_PLUGIN_ROOT` names an existing directory that is the `installPath` of some of them or lies inside it (compared by filesystem identity), `Installed:` comes from those entries alone, because the session runs that install and not a newer entry of another scope; if they name no version it is `(unknown)`, never the highest of the others or of the cache. Two names that are the same version in that order (`5.9` and `5.9.0`, or build metadata only) are told apart by their text, so the choice does not depend on the order of the directory listing. A leading `v` is dropped in one place (`dropV`), everywhere a version is compared, validated or named: `v5.8.0` and `5.8.0` are one version, as in the runtime (`parseSemver` in `scripts/session-start.mjs` and `parseVersion` in `src/utils/semver-compare.ts` both accept the optional `v`), so with the registry entries `v5.8.0` and `5.9.0` in different scopes `Installed:` is `5.9.0`. Step 1 prints the bare form on the `Installed:` line as it does on the `Latest:` line, which is how the runtime shows a version (its update notice writes `v` in front of a bare one). A cache directory is named by the bare version, so a version `v5.8.0` recorded in the registry names the directory `5.8.0`, and Step 4 compares the `OMC:VERSION` marker with the cached version without the `v` of either

## cache-guard

The rest of the guard of the cache repair commands (`cache-outdated`, `cache-stale`), the part that "Fix: Outdated Plugin" in SKILL.md does not carry. It applies to both commands:

Paths are compared after resolving symlinks one link at a time, and every link on the way is protected, not only the final directory (a pin on `5.7.0` in `5.7.0 -> 5.8.0 -> 5.9.0` protects all three; more than 40 links or a loop counts as unresolvable; the components of a path are read in the order the file system reads them, so a `..` after a link (`<dir>/shortcut/..`, where `shortcut` points to `5.9.0/nested`) names the parent of the link's target, and a `..` in a link's own target is read the same way, never folded as text first, except on win32, where Windows folds `..` first; every path that protects (the `installPath` of a pin or of another plugin, `OMC_PLUGIN_ROOT`, `CLAUDE_PLUGIN_ROOT`, an occupancy record) protects what it names read that way and also what the runtime reads from it, the same text folded, so `<cache>/ext/../5.9.0`, where `ext` is a link to a directory outside the cache, protects `5.9.0` by its text; a pinned `version` written with a leading `v` also pins the directory of the bare version, `v5.8.0` pins `5.8.0`); a link that nothing refers to is not protected just because its target is. Paths that exist are also compared by filesystem identity (device and inode), so two spellings of one directory are that directory on a volume that ignores letter case even where the platform reports `linux` (WSL2 on a Windows drive), and two directories whose names differ only in letter case stay two directories on a volume that tells letter case apart even where the platform reports `darwin` or `win32` (a case-sensitive volume): letter case is never folded by the name of the platform; the one exception only adds protection: the SessionStart publisher stores the plugin root of an occupancy record in lower case on win32 and the runtime compares records in that form, so on win32 a record also protects the version it names or lies inside by a lower-case comparison. Where a file system reports inode 0 (or a `stat` of the path fails) it gives no identity, on either side of a comparison, and nothing is then guessed from the spelling of a path: a path is judged by its exact text only when that text lies inside a cache version (or above the cache directory, where it names no version), and on win32 an occupancy record is also judged by the lower-case form above; every other path that protects or may protect a version, whatever the source (the `installPath` of a pin or of another plugin, `OMC_PLUGIN_ROOT` or `CLAUDE_PLUGIN_ROOT`, an occupancy record, a link on the way, a pinned `version` that names no directory by its exact spelling but a directory by another letter case; a path that does not exist is judged by its nearest existing parent), could be another name of a cached version that cannot be ruled out, so the command prints `Nothing moved: identity unavailable` and moves nothing, also when that path lies outside the cache on such a file system (two names of one directory that differ in letter case are then different, so the two variables naming one directory by two spellings count as a conflict and nothing moves). An exact spelling still protects the version it names and the free versions still move. If `installed_plugins.json`, an occupancy record or a path in them cannot be read or resolved completely (a path that does not exist adds no protection of its own, only through its nearest existing parent as described above; a key that contains `oh-my-claudecode` without being a supported ID, an empty or non-array entry list under any key, an entry under any key (also of an unrelated plugin) that is not an object or has neither a `version` nor an `installPath` or has one that is not a non-blank string (a `null` field counts as missing), and under a supported plugin ID a `version` that is not a semantic version (`999x.0.0`, `1.2`, `1.2.3.4`; the grammar of Step 1's `Latest:`, with the optional `v`; a `version` of another plugin has to be a non-blank string only), and, under a supported plugin ID, an `installPath` written as a Windows path (a drive letter such as `C:` followed by a backslash, or a UNC path) on a system other than Windows, where it names nothing that can be read (a registry written by Windows and read from WSL, say), an `installPath` of any entry that is not absolute (it names another directory for each directory the command runs in), and `OMC_PLUGIN_ROOT` and `CLAUDE_PLUGIN_ROOT` naming different directories (a variable that names no existing directory takes no part in that comparison, as in Step 1, but a path it names still protects the version it points into) all count as unreadable; the two variables are compared after resolving links and by filesystem identity, so two names of one directory are not a conflict), move nothing, and the message names the first cause it found in the registry (the key and the `version` or `installPath` of the entry, or that the file is not a regular file or not JSON of the expected shape); the cause may also be an entry of an unrelated plugin, an occupancy record or a plugin root variable, which the message does not name. The registry pins, the occupancy records and the plugin root variables are read again just before each version is moved, and a version that has become protected, or whose protection can no longer be read completely, is skipped and reported; only the instant between that last read and the rename remains open, because a SessionStart that has not yet published its record cannot be seen and the command holds no lock shared with the publisher. A version directory is not moved either when it, or any entry anywhere below it, was modified in the last 10 minutes (the same threshold, `STALE_THRESHOLD_MS` in `src/utils/paths.ts`, that SessionStart's own cleanup uses to leave a directory alone while an update may still be installing it; every entry at any depth counts because an update that refreshes an existing version overwrites its files in place and need not change the date of the directory itself or of any level above the file; a link is dated itself and never followed, and so is the version directory when it is a link: a redirect that SessionStart created a moment ago, such as `5.7.0 -> 5.8.0`, is as new as the link whatever the dates in its target and is left in place, and an old one is moved as the link only, so its target, in or outside the cache, is not touched): it is left in place and reported, and the command can be run again later; a version with a modification date more than 5 minutes in the future (a wrong clock, or files extracted from an archive) is left in place too and reported as that, not as a recent change. A version with more than 20000 entries (a cached version holds about 9000), or one whose entries cannot all be read, cannot be judged: it is left in place and reported (`Could not judge`). The updater (`copyPluginSyncPayload` in `src/installer/index.ts`) copies into the version directory in place and leaves no marker or lock file that the command could test, so an update that starts writing after the date scan has read the files it rewrites, up to the rename (the rest of the scan and the re-read of the registry, the records and the root variables run in between), cannot be seen; closing that window needs a lock or marker shared with the updater, which is a change in `src/installer` and not in this skill. The registry is read before any cache directory is looked for: when it cannot be read completely the command says so and stops, whatever namespace the cache lies in. The cache directory is `${CLAUDE_CONFIG_DIR:-~/.claude}/plugins/cache/<marketplace>/oh-my-claudecode`, where `<marketplace>` is the part after the `@` of each supported plugin ID the registry holds (`omc` for the bare `oh-my-claudecode`, and when the registry holds none): every such directory that exists is handled in turn, a pinned version protects the version of that name in each of them, and a backup from a marketplace other than `omc` carries its name in front (`<marketplace>-<version>-<time>`), and when more than one such directory exists every report line starts with `<marketplace>:` and its counts are those of that directory. A directory named `<version>.omc-stale-<pid>` (a name ending in `.omc-stale-` and a pid, what an interrupted cache relink leaves beside a missing or unusable original path) is not a version: the command does not list, protect, date or move it, because the reconciliation of SessionStart's own purge (`purgeStalePluginCacheVersions` in `src/utils/paths.ts`) restores it as the only intact copy and moving it to `plugins/backups` would prevent that. A directory whose name is not a semantic version of the grammar of Step 1 (`1e3`, `4.15.7L`, `v5.7.0`) is no version either: the command does not list, protect, date or move it, and leaves it where it is. A cache directory that exists but cannot be read (any error other than its absence, such as `EACCES` or `EIO`, or a file where the directory should be) is not an absent cache: the command prints `Nothing moved: could not read <directory> (<error code>)`, moves nothing and stops, and `No plugin cache found` or `No cache to clean` is printed only for a directory that does not exist (`ENOENT` with nothing on the path: a link to nothing is there and cannot be read, so it gives `Nothing moved: could not read <directory> (ENOENT: a link on the way points at nothing)`). The same holds for the registry file and the occupancy directory: an `ENOENT` is an absence only when nothing is on the path, and a link to nothing in their place, or in place of a directory above them (`.omc`), cannot be read, so the command refuses.

The backup directory is settled before the first move. `plugins/backups/oh-my-claudecode` is resolved the way the file system does, through every link on the way (for what does not exist yet, through its nearest existing parent), and the moves go to that real directory. It has to lie outside the plugin cache (the cache directory of every marketplace lies inside it), the marketplace clones, the occupancy records, the plugin root variables and every `installPath` of the registry (each as written and as a link makes it), and none of those may lie inside it: a link in the way that leads into a cached version would put the only recovery copy back where the next cleanup removes or relinks it. A tree that holds the destination as the configuration writes it, with no link involved (a plugin root that is the configuration directory itself), is no reason to refuse. An overlap, a destination that cannot be resolved (a link to nothing, a loop, a part of the path that cannot be examined) and one that cannot be compared (the file system reports no identity) end the command with `Nothing moved: the backup directory ...`, exit code 1, naming the destination and the tree. A link that leads somewhere outside those trees is allowed, and the `Moved` line then adds `(really <directory>)`. The check runs again before each move, and a destination that has changed fails the move with exit code 1.

## paths-and-locator

How a `..` in `CLAUDE_CONFIG_DIR` is folded, and how the locator line of each shell block finds the script (the note at the top of SKILL.md):

A `..` in the value is folded as text, as the runtime does (`path.normalize`: `.`, `..` and repeated separators), in the script and in the shell blocks alike, whether or not the directory exists (a path that goes through a link and then `..` names the parent of the link, not of its target, and a profile that is not there yet is created where the text names it; a relative value is read against the physical working directory, `pwd -P`, which is where `process.cwd()` and the file system start when the shell was entered through a link, not the logical `pwd -L`; the shell blocks make it absolute that way first and then fold the text themselves). A value that is a path of Windows (`C:\...`, `C:/...`, `\\host\share`, `//host/share`, `\...`) is kept as written in the shell blocks, not put under the working directory: the script reads it as absolute on Windows, where the file system folds a `..` in it as text. A relative path cannot be read once the working directory was deleted: the blocks and the script then print `current directory no longer exists` and end with exit code 1. The shell block of each script command starts with the same locator line: it takes the first of `CLAUDE_PLUGIN_ROOT` and `OMC_PLUGIN_ROOT` (surrounding spaces ignored) whose directory holds `scripts/omc-doctor.mjs`, skipping one that is unset or names no such file, then the global npm package `oh-my-claude-sisyphus` (`npm root -g`, asked through `node` with a limit of 5 seconds so that a hanging npm cannot stall the block, and only when neither variable has the file, so an install without a plugin root, such as `Channel: npm`, is still reached), and otherwise prints `omc-doctor: plugin files not found` and ends the block with exit code 1 (`CLAUDE_PLUGIN_ROOT` comes first because the skill was loaded from that plugin, so its script is the one that matches this text; the script reads both variables itself and decides the install channel from them, whichever copy of the file runs it).
